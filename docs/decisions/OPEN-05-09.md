## 1. Decision

Five questions, closed together because they are one shape of question and
splitting them would produce five near-identical records.

| Question | Category | Provider | Key |
|---|---|---|---|
| `OPEN-05` web search | `WEB_SEARCH` | **Tavily** | `TAVILY_API_KEY` |
| `OPEN-06` financial | `FINANCIAL` | **Financial Modeling Prep** | `FMP_API_KEY` |
| `OPEN-07` filings | `FILINGS` | **SEC EDGAR** | none — public |
| `OPEN-08` jobs | `JOBS` | **Adzuna** | `ADZUNA_APP_ID` + `ADZUNA_APP_KEY` |
| `OPEN-09` news | `NEWS` | **Tavily**, news mode | `TAVILY_API_KEY` |

`REQ-TOOL-003` (page fetch) is already implemented and named no provider; it is
not part of this decision.

---

## 2. What this plugs into — unchanged

Each provider is a class satisfying the `Tool` protocol, registered by
category. The orchestrator selects a category and never learns which provider
answered (`REQ-TOOL-009 AC-2`). This decision therefore changes the registry
and nothing above it — which is the property the whole tool contract was built
to have, and the first real test of whether it holds.

---

## 3. Why these, honestly

These were **already chosen** — keys for four of them were in
`services/api/.env` before this record existed. What this document does is make
that explicit and reviewable rather than implicit in a gitignored file, which
is the difference between a decision and an accident.

That framing matters for how much weight the rationale below carries. It is
justification for a defensible set of choices, not the output of a procurement
exercise. Each row is independently replaceable, and §7 records what would
prompt a change.

### 3.1 `OPEN-05` and `OPEN-09` — Tavily, for search and news

One vendor serving two categories is unusual enough to name. It is acceptable
here because the registry keys on category, so the two are separate
registrations that happen to share a client, and either can be replaced without
touching the other.

Tavily answers `REQ-TOOL-002 AC-1` (ranked results with URLs) directly, and its
news mode carries a publication date distinct from the retrieval timestamp,
which is exactly what `REQ-TOOL-007 AC-1` requires and what Update Research
change detection reads (`AC-3`).

**This is the weakest row in the table.** A general search API in news mode is
not a news API: it has no editorial metadata, no wire-story deduplication, and
no notion of which outlets are established — which `REQ-TOOL-007 AC-2` asks for
and `DEC-08` has to supply from its own allowlist instead. It is chosen because
it works with a key that already exists and unblocks the category now.
Revisiting it is cheap and §7 says when.

### 3.2 `OPEN-06` — Financial Modeling Prep

Covers `REQ-TOOL-004`'s three criteria: values carry a reporting period
(`AC-1`), currency and units are exposed for normalization (`AC-2`), and
estimates are distinguishable from reported figures (`AC-3`). That third one
disqualifies several cheaper alternatives, and it is not cosmetic — `DEC-10`
depends on it, because an estimate disagreeing with a reported figure is not a
conflict and must not be counted as one.

### 3.3 `OPEN-07` — SEC EDGAR

The only row with no key, and the easiest call in the table. It is the
authoritative source, so `REQ-TOOL-005 AC-1` (filing-derived sources are
primary tier) is true by construction rather than by assertion. Its URLs
address a specific accession number, which is precisely `AC-3`: a citation
resolves to the filing, not to a search page.

Its limit is scope: US registrants only. Non-US subjects have no filings
category available and will produce a gap the report names — which is the
designed behaviour for a category with no provider, not a new failure mode.

### 3.4 `OPEN-08` — Adzuna

Aggregates postings with company attribution, which `REQ-TOOL-006 AC-1` needs
to tell an official company posting from a recruiter's repost. Carries
retrieval timestamps for `AC-2`. Salary data arrives as ranges with a stated
basis, which is what `AC-3` requires before any salary figure may be shown.

---

## 4. What every one of these has in common

They are all **untrusted content sources**, and none of them is special. Each
returns `ToolItem`s whose content is `Untrusted`; each classifies its failures
into the closed `FailureKind` set; each returns rather than raises. A provider
that cannot say where an item came from cannot construct a `ToolItem` at all
(`REQ-TOOL-012 AC-2`).

A specific trap, named because four of these are JSON APIs rather than web
pages: **structured provider output is not more trustworthy than HTML.** A
company description field returned by a financial API is attacker-influenced in
exactly the way a web page is. It is `Untrusted` too.

---

## 5. Keys and configuration

Every key is read from environment config and validated at startup
(`REQ-SEC-007 AC-3`). A category whose key is absent **does not register**, and
the run reports it as a gap the same way it reports an unconfigured category
today — degraded, never silent.

`services/api/.env` is gitignored and must stay so. The keys currently in it
are development credentials; production keys are a deployment concern and are
not this record's business.

---

## 6. Consequences

### 6.1 Code

Five tool implementations under `scrapr_core/tools/impl/`, each beside — not
instead of — the fixture that proves the contract (§15). Registration moves
from the worker's hardcoded fixture list to a config-driven builder, because
five conditional registrations inline is where that function stops being
readable.

### 6.2 Testing

Fixture per tool for contract tests; recorded cassette per tool for integration
tests. §15 has said this since Phase 0 and could not be acted on because there
was no provider to record. There is now.

### 6.3 Cost

Five metered APIs on the tool-call counter. `RUN_CEILING_TOOL_CALLS` is
currently an operational backstop at 120 and was set when calls were free.
Phase 8 (`TBD-04`, `TBD-10`) should revisit it against real per-call prices.

---

## 7. What would prompt a change

Recorded so a revisit is a decision rather than a drift:

- **News** — if conflict detection starts reporting the same wire story as
  corroboration from three outlets, the news row is the cause and a dedicated
  news API with outlet metadata is the fix.
- **Filings** — a non-US subject appearing in real use.
- **Any row** — rate limits that make the per-area allocation unachievable, or
  a pricing change that moves the run cost past `TBD-10` once it is set.

---

## 8. Known risk

**Four vendors, one of them serving two categories.** `REQ-TOOL-009` makes each
replaceable, and the fixtures mean the pipeline is testable without any of
them. But a Tavily outage now degrades two categories at once, and the report
will name both as gaps in the same run — which will read as a much worse
research failure than it is.
