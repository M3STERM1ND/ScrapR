Three questions in one record because each one's answer is a precondition of
the next. Who an account is decides what claiming anonymous research means, and
what claiming means decides what deletion has to reach.

---

## `DEC-16` — Authentication mechanism (`OPEN-11`)

**First-party email and password, verified by the FastAPI service, with
server-side sessions in Postgres.**

| Element | Decision |
|---|---|
| Credential | Email (case-insensitive, `citext`) and a password of 12 to 256 characters. No composition rules (NIST SP 800-63B §5.1.1.2). |
| Storage | Argon2id via `argon2-cffi` defaults, in `users.password_hash`. Rehashed on sign-in when the parameters change. The password is never stored or logged in recoverable form (`REQ-AUTH-009 AC-1`). |
| Session | A 256-bit token in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie named `scrapr_account`. Only its SHA-256 is stored, in `user_sessions`. A new token on every sign-in; sign-out revokes the row. |
| Lifetime | 30 days absolute from sign-in. No refresh token and no sliding extension: a session that outlives its purpose is a liability, and signing in again costs one form. |
| Precedence | An account session outranks an anonymous one. A request carrying both acts as the account. |
| Rate limits | Sign-in and sign-up are limited per client address and per email, in Postgres so the limit holds across processes (`REQ-AUTH-009 AC-3`). |
| Enumeration | Sign-in failure is one message whether the email exists or not, and an unknown email still pays for an Argon2 verification so timing does not tell them apart. |

### Why not a hosted provider

Clerk, Auth0 and Supabase Auth would each have been faster to wire. All three
were rejected for the same reason: **authentication here is a persistence
feature** (masterplan §17), not an identity platform, and a hosted provider
moves every account's email to a third party, adds a second session system to
keep in agreement with the API's ownership checks, and puts an external
dependency on the path to reading one's own research.

The deciding constraint is `OwnerContext`. Ownership is enforced in
repositories against a user id the API resolves (implementation plan §4.3). A
first-party session resolves that id in one indexed query. A hosted provider
resolves it by verifying a JWT the API did not issue, and the product then has
two places that can disagree about who is signed in.

### Why not magic links

A magic link needs outbound email, and outbound email needs a provider, a
verified sending domain and credentials this project does not yet have. That is
a real cost to take on for V1 and the reason for deferring it rather than a
judgement that passwords are better.

### Known gap: no password reset

**V1 has no password reset and no email verification**, because both need
outbound email. A user who forgets a password cannot recover the account. This
is recorded, not glossed: it is the first thing to add once an email provider is
chosen, and the `users` shape already accommodates it (a reset token table is an
addition, not a change). Until then, the sign-up form says plainly that the
password cannot be recovered.

## `DEC-17` — Anonymous sessions and claiming (`OPEN-17`)

The identity half was built in Phase 0 (implementation plan §8). This decides
the semantics half.

| Question | Answer |
|---|---|
| **How is it identified?** | Unchanged: a 256-bit token in the `scrapr_session` cookie, stored as a SHA-256. |
| **How long does it survive?** | **30 days since last activity.** `last_seen_at` is refreshed at most once an hour, and `expires_at` moves with it. The cookie's `Max-Age` is set to match whenever the row is refreshed. |
| **Does it expire?** | Yes. An expired session resolves to nobody: its research is unreachable at once, whether or not the purge has run yet. |
| **Is expired research deleted?** | Yes, under `DEC-18`. There is no archive of research nobody can reach. |
| **Eligibility window for claiming** | Any time while the anonymous session is valid — unexpired and not already claimed. |
| **Mechanism** | Automatic on sign-up and on sign-in when the request carries a valid anonymous cookie, and explicitly through `POST /v1/research/claim` for an account that is already signed in. |

### What a claim does

One transaction (`REQ-AUTH-004`, implementation plan §8):

1. Every research session whose `anonymous_session_id` is the caller's resolved
   anonymous session gets `owner_user_id` set and `anonymous_session_id`
   cleared. The `one_owner` check constraint holds at every row.
2. The anonymous session row records `claimed_by_user_id` and `claimed_at`.
3. The anonymous cookie is cleared on the response.

**`AC-2` is structural.** The statement's only selector is the anonymous
session id resolved from a token the caller presented. There is no request
parameter naming a research session, so there is no call shape that transfers
research owned by another account or another anonymous session.

A claimed anonymous session never resolves again. Its research has moved, and a
token that once owned it must not quietly start owning new research on a
different browser tab.

Uploads, versions, conversation and exports are reached through the session,
so they move with it and nothing else needs rewriting (`REQ-AUTH-006 AC-1`).
A run still in flight when the claim lands continues: the runner rebuilds the
owner from the session row at every step (`REQ-SEC-011`).

## `DEC-18` — Deletion semantics (`OPEN-24`)

**Hard delete. No retention window, no recovery.**

### A research session

| Step | When | What |
|---|---|---|
| 1. Hide | In the request | `deleted_at` is set. Every read already filters on it, so the session is gone from every API path immediately. |
| 2. Stop | In the request | Outstanding steps of every run are marked `dead` and the runs `failed`, so no worker picks the work up again. |
| 3. Remove files | In the request | Every upload object and every export artifact is deleted from storage (`REQ-SEC-008 AC-2`, `REQ-EXP-008 AC-3`). A storage failure does not undo steps 1 and 2; the purge retries the objects. |
| 4. Purge rows | Within 30 minutes | The maintenance sweep deletes every row: versions, sources, evidence, claims, conflicts, sections, visualizations, questions, conversation, uploads and chunks, exports, activity, runs, steps and tool invocations (`AC-1`). |

The gap between 1 and 4 exists for exactly one reason: a worker may be
executing a step of that run right now. Deleting rows out from under it would
turn a user's deletion into a worker crash. A step can run for as long as the
run's wall-clock ceiling (fifteen minutes), so the grace period is twenty, and
the sweep runs every five.

**Prior versions and exports go with the session.** A version cannot be deleted
on its own: `REQ-VER-002` makes versions immutable, and deleting one would
silently change what "version 3" meant.

### An upload

The file and its searchable chunks go immediately; the row stays, soft-deleted,
carrying only its filename and metadata. That is `REQ-AUTH-008 AC-3`: a prior
version records that the document existed rather than having its evidence base
silently change. Evidence excerpts a version already quoted from the document
remain part of that version's record until the session itself is deleted, and
the workspace marks the citation as coming from a document that has since been
removed.

This is a real trade and it is stated as one: deleting a document stops it
informing any future research, and does not rewrite the past.

### Expired anonymous research

Purged by the same sweep, through the same code path, once the anonymous
session has been expired for the grace period. There is no second deletion
implementation to drift from the first.

### What this does not decide

- **Database backups.** Hosted Postgres keeps point-in-time backups for a
  provider-set window, and a hard delete does not reach into them. Database
  hosting is `N-01` and still open; whichever provider is chosen, its backup
  retention should be configured to 7 days or fewer and stated in the privacy
  notice.
- **Account deletion.** No V1 requirement asks for it. A user can delete every
  piece of research they own; removing the account row itself is left for when
  a requirement names it.

## Consequences

- **Schema (migration `0005`):** `users.password_hash`, a `user_sessions`
  table, a `rate_limit_counters` table, and an index on
  `research_sessions(deleted_at)` for the sweep. No existing column changes
  meaning.
- **Code:** an account repository, a claim operation, a deletion service and a
  purge sweep in `scrapr_core`; auth and history routes in the API; the sweep
  runs from the worker loop.
- **Testing:** `REQ-SEC-002 AC-3` becomes a suite that enumerates every route
  with a research identifier and asserts another account, another anonymous
  session and a signed-out visitor all read it as absent.

---

## Known risk

**No password reset is the one users will feel.** It is the direct cost of not
having outbound email, and every other part of this record is independent of
it. The trigger for revisiting is simple: the first support request from
someone locked out of saved research.
