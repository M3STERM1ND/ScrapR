Phase 8 is where a product stops being a demo, and these four questions are the
numbers and the topology that decide it. They are recorded together because
each constrains the others: the concurrency target sets how many workers run,
the cost ceiling sets how much each one may spend, and the rate limits are what
keep anonymous traffic inside both.

---

## `DEC-23` — Rate limiting and abuse controls (`OPEN-18`)

**Every expensive action is counted against three subjects at once: the
browser's session, the account if there is one, and the client address.** A
request must be within all of its limits. Counters live in Postgres
(`rate_limit_counters`, `DEC-16`), so every API instance enforces the same
allowance.

| Action | Per anonymous session | Per account | Per client address |
|---|---|---|---|
| Start research (new, follow-up research, Update Research) | 5 / hour, 15 / day | 20 / hour, 100 / day | 30 / hour |
| Ask a follow-up question | 30 / hour | 120 / hour | 150 / hour |
| Request an upload | 20 / hour | 60 / hour | 80 / hour |
| Request an export | 20 / hour | 60 / hour | 80 / hour |
| Sign in | — | 10 / 15 min per email | 20 / 15 min |
| Sign up | — | — | 10 / hour |

### Why three subjects

The anonymous flow has no account to attribute usage to, which is the whole of
`OPEN-18`. Each subject alone fails in a known way:

- **Per session alone** is defeated by clearing cookies: a new session is one
  request away.
- **Per address alone** punishes an office or a university behind one address,
  and does nothing about a botnet.
- **Per account alone** does not exist for anonymous traffic.

Together, clearing cookies buys at most the address limit, and a shared address
still gives each person their own session allowance up to the address ceiling.
The address is read from `X-Forwarded-For` only behind a proxy the deployment
controls (`TRUST_PROXY_HEADERS`), never from a header any client may set.

### Load shedding

Beyond per-subject limits, research admission is refused with a `503` and a
plain message when the queue is past `TBD-13` (see `DEC-24`). A refused request
is a clear "busy, try again shortly", never a run that sits unclaimed for an
hour.

### Other abuse controls

- **Request bodies over 1 MB are refused** before they are parsed. No route in
  this API needs more; uploads go straight to storage.
- **State-changing requests must come from an allowed origin.** A request with
  an `Origin` header outside `WEB_ORIGINS` is refused, on top of `SameSite=Lax`
  cookies.
- **Errors say nothing internal** (`REQ-SEC-010 AC-5`), unchanged since Phase 0
  and re-tested.

## `DEC-24` — The `TBD` values (`OPEN-23`)

**These are initial targets, not measurements.** `PRD §9.6` asks for values set
from Phase 1 and Phase 3 measurements; no production traffic exists yet, and
local runs use a deterministic stand-in model and fixture tools that are faster
and cheaper than real ones by construction. What exists instead is the set of
ceilings the pipeline already enforces, the providers' documented behaviour,
and the local render and pipeline timings. The values below are derived from
those, and every one of them is now **measured in production by the
observability `DEC-24` switches on** (`REQ-OBS-003 AC-3`), so the first real
week of traffic can confirm or move each one with data rather than opinion.

| TBD | Requirement | Value | How it is held |
|---|---|---|---|
| `TBD-01` | Maximum objective length | **2,000 characters** | Schema bound, since Phase 1 |
| `TBD-02` | Individual tool call timeout | **30 seconds** | `ToolBudget.timeout_seconds`; a timeout is a typed failure, not a hang |
| `TBD-03` | Research run p50 completion | **4 minutes** | Measured per run (`research_runs.started_at`/`finished_at`) and reported by `scrapr-ops` |
| `TBD-04` | Hard ceiling on a run | **15 minutes** | `RUN_CEILING_WALL_CLOCK_SECONDS`; the run ends with `termination_reason = ceiling` and reports partial results |
| `TBD-05` | Maximum silent interval during research | **30 seconds** | The research step emits a progress event whenever 20 seconds pass without one |
| `TBD-06` | Workspace render p95 | **2.5 seconds** | One denormalised version payload; checked by the Lighthouse budget in CI for the landing surface, and to be added to real-user monitoring once a provider is chosen |
| `TBD-07` | Conversational answer p50 | **8 seconds** | One `STANDARD` model call over stored evidence; latency logged per answer |
| `TBD-08` | PDF generation p95 | **30 seconds** | Local render ~0.1 s; the budget is queue wait plus render. `exports.render_ms` recorded |
| `TBD-09` | PowerPoint generation p95 | **30 seconds** | As above |
| `TBD-12` | Concurrent in-flight runs | **20** | One step at a time per worker process; the worker count is the concurrency, so 20 is 20 worker replicas at peak |
| `TBD-13` | Queue depth shed threshold | **100 pending runs** | New research is refused with `503` beyond it (`DEC-23`) |

`TBD-10` and `TBD-11` are `DEC-25`.

## `DEC-25` — Cost ceilings (`OPEN-29`)

| TBD | Run | Ceiling |
|---|---|---|
| `TBD-10` | A research run (first research, or follow-up research) | **$2.00** |
| `TBD-11` | An Update Research run | **$1.50** |

### What counts

Every model call's tokens are metered and priced from the `DEC-06` tier table,
and every tool call is charged at its provider's per-call price (web and news
search at Tavily's advanced-search rate; financial data, filings, jobs, page
fetch and documents at zero, because they are flat-rate or free). The ledger is
per run and per stage, stored on `research_runs.tokens` and
`research_runs.cost_micros` (`REQ-OBS-004`, `REQ-OBS-005`).

### What happens as a run approaches it

The run budget already stops *before* a call that it cannot afford, not after
(`DEC-04 §5`). With cost metered, the cost counter joins wall clock and tool
calls as a live limit:

1. Retrieval stops starting new tool calls once the remaining cost budget is
   spent. Areas not yet researched are reported as not reached, by name.
2. Synthesis still runs, on the evidence gathered. A report that ran out of
   budget is a partial report, never no report.
3. The run ends with `termination_reason = ceiling`, the version is `partial`,
   and the reader sees the shortfall notice.

An update is capped lower than a first run because it re-asks questions already
planned and skips interpreting and planning; if updates routinely hit $1.50,
that is a signal about retrieval volume to investigate, and `scrapr-ops` lists
every run over 80% of its ceiling for exactly that reason.

## `DEC-26` — Where workers run, and what dispatches them (`OPEN-03`)

`PRD §11.5` says selecting a queue technology does not close `OPEN-03` without
saying where workers execute and how a run longer than a serverless limit
survives. Both halves:

| Question | Answer |
|---|---|
| **Dispatch** | **Postgres.** Workers claim work with `SELECT … FOR UPDATE SKIP LOCKED` over `run_steps`, `uploads` and `exports`. No Redis and no hosted queue: the durable record already is the queue (implementation plan §5.6), and a second system would be a second source of truth about the same job. |
| **Where workers execute** | **A long-running container, off Vercel.** `scrapr-worker` is a plain process; any container host that runs one process continuously and reaches Postgres and R2 is a valid target. The API and the web app stay on Vercel (`DEC-03`). |
| **A run longer than a serverless limit** | Not a failure mode: the worker is not serverless. Independently, every step is idempotent and checkpointed, so a worker restart mid-run reclaims the step after its lease (`NFR-REL-001`). |
| **Scaling** | Add worker replicas. `SKIP LOCKED` makes them safe to run in parallel with no coordination; `TBD-12` is the replica count at peak. |

**Deliberately not decided here: the container host vendor.** Fly.io, Render,
Railway and ECS all satisfy the table above, and choosing between them is a
billing and account decision that changes no code and no configuration shape.
It is recorded as a deployment step in the README, alongside database hosting
(`N-01`), which is likewise a provider choice with no code consequence.

## `REQ-SEC-006` — Least privilege, made concrete

| Credential | API | Worker | Why |
|---|---|---|---|
| `DATABASE_URL` | Yes (role without DDL) | Yes (role without DDL) | Migrations run as a separate owner role, by hand (`README`) |
| Storage keys | Yes | Yes | The API presigns; the worker reads uploads and writes exports |
| `ANTHROPIC_API_KEY` | Yes | Yes | The API answers follow-ups; the worker researches |
| Tavily, FMP, Adzuna, EDGAR agent | **No** | Yes | Only research retrieves |

In production the API **refuses to start** holding a data-provider key: a
credential a process does not use is one it can leak. The database roles are
provided as `infra/postgres-roles.sql`.

## Consequences

- **Schema (migration `0007`):** `research_runs.failure_stage` and
  `failure_kind` so failures are queryable by cause (`REQ-OBS-001 AC-2`);
  `tool_invocations.source_domain` and an index for per-domain source failures
  (`REQ-OBS-006`); `exports.render_ms` (`REQ-OBS-003`).
- **Code:** a metering provider wrapper and per-run ledger; tool invocation
  recording in the registry; progress heartbeats in the research step; rate
  limit and admission checks on the expensive routes; origin and body-size
  guards; `scrapr-ops report` for operators.
- **Testing:** every limit and the shed threshold, cost-ceiling termination,
  tool telemetry, the heartbeat, and a web-page injection corpus through the
  whole pipeline to go with the documents corpus.

---

## Known risk

**Every number in `DEC-24` and `DEC-25` is a first estimate.** The mitigation is
not better guessing; it is that each is now measured, reported and a single
configuration value away from changing. The first thing to do with production
traffic is run `scrapr-ops report` and replace estimates with medians.
