Three questions in one record because they are one question wearing three
hats: what a user may upload, and what the system does with it. Splitting them
would produce three records that all cite each other.

---

## `DEC-13` — Upload limits (`OPEN-19`)

| Limit | Value |
|---|---|
| Maximum file size | **25 MB** |
| Maximum files per session | **10** |
| Maximum total per session | **100 MB** |

Note that 10 × 25 MB is 250 MB and the session cap is 100 MB. That is
deliberate: the per-file limit is about what one document plausibly is, and the
session limit is about what the system will process for one research run. A
user with four large filings hits the total before the count, and a user with
ten short memos hits the count before the total. Both are real shapes.

**Enforced server-side, twice** (`REQ-DOC-010 AC-1`, plan §10). Once at presign
— refuse to sign a URL for a file that would breach a limit — and again at
`complete`, because a presigned URL is not a limit. A client that lies about
`size_bytes` gets a signature it cannot usefully redeem.

These are product numbers and nothing derives from them, so changing one is a
configuration change. What is not negotiable is that all three are checked in
both places.

## `DEC-14` — Supported types (`OPEN-20`)

| Accepted | Extension | Why |
|---|---|---|
| PDF | `.pdf` | `REQ-DOC-001` names it |
| Word | `.docx` | `REQ-DOC-001` names it |
| Spreadsheet | `.xlsx`, `.csv` | `REQ-DOC-001` names it; CSV because exported data usually arrives this way |
| Plain text | `.txt`, `.md` | Costs nothing to support and covers pasted notes and READMEs |

**Rejected for V1**, each for a reason rather than by omission:

- **Legacy `.doc` and `.xls`** — different binary formats needing separate
  parsers, for files a user can convert in one step.
- **`.pptx`** — extractable, but a deck is titles and fragments, and
  `REQ-EVID-007` wants evidence with a verbatim excerpt that supports a
  statement. Slide text rarely is one.
- **Images and scanned PDFs** — needs OCR, which is a different failure mode
  with its own accuracy question. A scanned PDF that extracts no text becomes a
  `failed` upload with a message saying so (`REQ-DOC-004 AC-3`), which is the
  honest outcome rather than a silently empty document.

`AC-2` requires an unsupported type be rejected with a message naming what is
supported, and the list above is that message.

**Type is determined from content, not from the filename.** A `.pdf` extension
is a claim the client makes; the magic bytes are what the file is. `REQ-SEC-005`
and the `Upload.content_type` docstring both already say the stored value is
"what the file actually is, not what the client asserted".

## `DEC-15` — Retrieval within documents (`OPEN-12`)

**PostgreSQL full-text search. No vector search in V1.**

`OPEN-12` asks whether V1 actually needs vectors. It does not, and the reason
is the shape of the corpus rather than a general position on embeddings.

**The corpus is one user's handful of documents**, bounded by `DEC-13` at ten
files and 100 MB. Vector search earns its cost on large corpora where the
user's words and the document's words diverge and recall collapses. Over ten
documents the reader chose and can name, keyword recall is high, and the
research questions arrive already using the subject's vocabulary — they were
written by a model that read the objective.

**`REQ-TECH-007` prefers a Postgres extension to a second datastore**, and
implementation plan §10.4 says the same: "keyword search may well be enough for
V1, and Postgres full-text search is the fallback if vector search is
deferred." This is that deferral, made explicit.

**What this costs.** A question phrased entirely in synonyms of what the
document says will miss. That is a real limitation and the mitigation is
ordinary: `tsquery` over `to_tsvector` with English stemming handles inflection,
and the tool returns passages rather than a single best match
(`REQ-DOC-005 AC-2`), so a partial term hit still surfaces the surrounding
chunk.

**What would change this.** Documents becoming large or numerous — a user
uploading a hundred filings rather than the ten `DEC-13` allows — or repeated
evidence of a miss where the answer was plainly in an uploaded file.
`pgvector` is a Postgres extension, so adopting it later adds a column and an
index rather than a datastore, which is exactly why `REQ-TECH-007` prefers that
route and why deferring is cheap.

---

## Consequences

- **Schema:** none. `uploads`, `upload_chunks` and `chunk.locator` are all in
  the baseline. Full-text search needs a `tsvector` index on `upload_chunks`,
  which is an index rather than a shape change.
- **The document tool** implements the same `Tool` contract as every external
  provider (`REQ-TOOL-008`, `REQ-DOC-005 AC-1`). `DOCUMENTS` is already in
  `TARGETED_CATEGORIES`, so the planner never selects it — a document tool
  answers "search this upload", not "tell me about Acme".
- **Testing:** `REQ-DOC-009 AC-3` requires an explicit adversarial case, and
  `tests/adversarial/` has been specified since Phase 0 without existing. Phase
  4 is where that debt comes due.

---

## Known risk

**`DEC-15` is the one that will look wrong first.** Full-text search fails
visibly and specifically — a user watching the agent miss a figure that is
plainly in their PDF — where its cost is a search that quietly retrieves
slightly worse passages. The failure is legible, which makes it feel like the
wrong call more often than it is one; the numbered trigger above exists so that
reversing is a measurement rather than a reaction to the first miss.
