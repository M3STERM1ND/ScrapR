## `DEC-21` — Generation approach (`OPEN-21`)

**Both formats are generated in the worker, in Python, from a renderer-agnostic
document built from the version's rows. No browser, no model, no network call.**

| Format | Library | Charts | Tables |
|---|---|---|---|
| PDF | **ReportLab** (`platypus` for flow, `graphics` for charts) | Vector, drawn from the stored `visualizations.spec` | ReportLab tables |
| PowerPoint | **python-pptx** | **Native, editable PowerPoint charts** from the spec's points | Native tables |

### The pipeline

```
version rows ──build_document──▶ ExportDocument ──render(theme)──▶ bytes ──▶ object storage
```

1. **`build_document`** reads sections, claims, evidence, sources, conflicts,
   visualizations and What's Changed for one version and produces a plain value
   object. It is the only step that touches the database, and it contains no
   text the version does not contain (`REQ-EXP-005 AC-1`).
2. **A renderer** takes that document and a theme and returns bytes. Renderers
   make no decisions about content — which claims, in what order, with which
   citations — only about presentation. That split is `REQ-EXP-004 AC-3`.
3. **The worker stores** the artifact under an unguessable key and marks the
   export ready. The API only ever issues a five-minute signed download URL to
   the research's owner (`REQ-EXP-008`).

### Why these, and not the alternatives

- **A headless browser (HTML to PDF)** — rejected by `DEC-11 §7.2` for charts,
  and the reasons apply to the whole document: a Chromium binary in the export
  path, on a deployment whose worker host is still `OPEN-03`. It would also
  give PowerPoint nothing; a second pipeline would be needed anyway.
- **WeasyPrint** — good HTML/CSS layout, but it needs Pango and Cairo as system
  libraries. That is a native dependency on every worker host and every
  developer machine, for one of two formats.
- **LibreOffice conversion** — one source, two outputs, and a 500 MB runtime to
  get there. Conversion fidelity for charts is also the weakest part of it.
- **Model-generated layout** — forbidden outright by `REQ-EXP-004 AC-1`.

ReportLab and python-pptx are both pure Python wheels with no system
dependencies, both mature, and both deterministic: the same version and theme
produce the same document every time, which is what makes an export failure
retryable without re-running research (`NFR-REL-003`).

### Native charts in PowerPoint

`REQ-EXP-002 AC-2` requires visualizations to render as slide content, not
broken placeholders. A native chart is the strongest reading of that: the
reader can restyle or re-plot it in PowerPoint, and it never pixelates on a
projector. The spec already carries labelled points (`DEC-11 §4`), which is
exactly what a chart's data sheet needs. The PDF draws the same points as
vectors, so the two formats agree with each other and with the workspace.

### Fonts

The PDF **embeds** its fonts, so it looks the same everywhere: Noto Sans and
Noto Serif (SIL Open Font License, bundled under `scrapr_core/export/fonts`),
which cover Latin, Greek and Cyrillic. The PowerPoint file **names** its fonts
rather than embedding them, as PowerPoint expects, choosing families present on
any Windows or macOS install (Calibri, Georgia, Arial, Cambria) so it does not
fall back to something unplanned.

**Known limit:** text in scripts Noto Sans does not cover — Chinese, Japanese,
Korean — renders as missing glyphs in the PDF. The PowerPoint file is
unaffected. Bundling Noto CJK costs 15 MB or more; that is deferred until a
reader needs it.

### The job

Exports run through the worker, like research, but not through `run_steps`: an
export is one unit of work with no stage to resume from, and the research run
machinery closes versions and moves session status, neither of which an export
may touch. Instead the `exports` row is itself the job, with a lease:

| Column | Purpose |
|---|---|
| `status` | `pending` → `running` → `ready`, or `failed` |
| `attempts` | Three attempts, the same limit as a research step (`STEP_MAX_ATTEMPTS`) |
| `lease_expires_at` | A worker that dies mid-render loses the export after five minutes; another takes it |
| `error` | A sentence written for the reader, never a stack trace |

A failed export is retried by the reader, from the export panel, without
re-running research (`REQ-EXP-007 AC-3`, `NFR-REL-003`).

## `DEC-22` — The six themes (`OPEN-22`)

The masterplan names six. Each is a fixed definition in
`scrapr_core/export/themes.py`; nothing about a theme is chosen per export
(`REQ-EXP-004 AC-1`).

| | Professional | Investor | Modern | Corporate | Minimal | Dark |
|---|---|---|---|---|---|---|
| **For** | Client-ready business brief | Financial audience, figures first | Creative and product teams | Internal and board papers | Reading, printing | Screens and technical teams |
| **Ground** | White | White | Warm off-white `#FBF7F2` | White | White | Near-black `#0F1419` |
| **Text** | `#1D2530` | `#14213D` | `#22223B` | `#222222` | `#111111` | `#E6EDF3` |
| **Muted** | `#52606D` | `#4A5568` | `#5C5470` | `#555555` | `#595959` | `#9DA7B3` |
| **Accent** | Navy `#1F4E79` | Green `#1B5E20` | Terracotta `#B4442A` | Teal `#00695C` | Ink `#111111` | Cyan `#39C5CF` |
| **Headings** | Sans, bold | Serif, bold | Sans, bold, large | Sans, bold, on a band | Serif, regular | Sans, bold |
| **Body** | Sans | Sans | Sans | Sans | Serif | Sans |
| **Cover** | Title with an accent rule | Title over a key-figures strip | Full-width accent block | Accent band across the top | Title and date, nothing else | Title on dark with an accent rule |
| **PowerPoint fonts** | Calibri | Georgia / Calibri | Arial | Calibri | Georgia | Arial |

**Contrast.** Text and muted text meet WCAG AA (4.5:1) against their ground in
every theme, and so does any accent used for text. This is checked by a test,
not by eye.

### What every theme keeps

The distinctions `REQ-EXP-009` requires survive every theme, on channels that
are not colour (`REQ-SYNTH-002 AC-3`, `NFR-USE-002`, `DEC-11 §5`), so a printed
greyscale copy of any theme loses nothing:

| Distinction | Channel in every theme |
|---|---|
| Claim type | The word (**Fact**, **Analysis**, **Forecast**, **Uncertainty**) before the claim, and a left rule: solid, dashed, dotted, or none |
| Confidence | The word (High, Moderate, Low confidence) after the type |
| Citations | Numbered markers after each claim, resolving to a numbered source list with tier and retrieval date |
| Conflicts | A labelled "Sources disagree" block beneath the claim, both values and both sources named |
| Chart series | Position and markers; at most one accent series |
| Version | "Version N · generated from research dated …" on the cover and in every page footer or slide footer (`REQ-EXP-006 AC-2`) |

## Consequences

- **Dependencies:** `reportlab`, `python-pptx`, and four OFL font files.
- **Schema (migration `0006`):** `exports.attempts`, `exports.lease_expires_at`,
  `exports.size_bytes`, and an index for claiming pending exports.
- **API:** `POST /v1/research/{id}/versions/{n}/exports`,
  `GET /v1/research/{id}/versions/{n}/exports`, `GET /v1/exports/{id}` (with a
  signed URL once ready), `POST /v1/exports/{id}/retry`.
- **Security:** retrieved text is escaped before it reaches ReportLab's
  paragraph markup, characters XML cannot hold are removed before they reach a
  PowerPoint part, and only `http` and `https` links are made clickable.

---

## Known risk

**Layout is fixed per theme, and content is not.** A report with one very long
section or an unusually long claim will produce a slide that is dense. Slides
split claims at a fixed count and truncate nothing, so the failure is a crowded
slide rather than lost content. If readers find that the most common complaint,
the answer is a smarter split, not generated layouts.
